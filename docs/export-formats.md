# Export formats

Seven exporters, all producing Hebrew in correct right-to-left form. Registry:
`apps/backend/tiktuv/exports/__init__.py`.

| Format | Extension | Encoding | Line endings | RTL mechanism |
|---|---|---|---|---|
| Plain text | `.txt` | UTF-8 + BOM | CRLF | Leading RLM, per-paragraph neutral marks |
| Timestamped text | `.timestamped.txt` | UTF-8 + BOM | CRLF | RLM after each stamp |
| Word | `.docx` | OOXML | — | `w:bidi` at section + paragraph, `w:rtl` at run |
| PDF | `.pdf` | PDF | — | Bidi applied at paint time (see below) |
| SubRip | `.srt` | UTF-8, **no BOM** | CRLF | Trailing RLM on neutral-final cues |
| WebVTT | `.vtt` | UTF-8, no BOM | LF | `direction:rl align:right` cue settings |
| JSON | `.json` | UTF-8, no BOM | LF | Logical order, `ensure_ascii=false` |

## The rule that governs all of them

Text is stored, edited and exported in **logical order** — the order the words
were spoken. The only place character order changes is when painting a PDF,
because PDF has no bidirectional text engine. Everywhere else the Unicode bidi
algorithm does the work at display time.

This matters practically: a "helpfully" reversed file looks right in one viewer
and is corrupt in every other, and breaks copy-paste, search and diff.

## Plain text

Paragraphs separated by a blank line, split on long silences and speaker
changes when those options are on.

The BOM is deliberate: without it, Notepad and Excel guess the system code page
and mangle Hebrew. SRT gets no BOM because some hardware players reject it.

A leading RLM makes the file open right-aligned in editors that infer direction
from the first strong character.

## Timestamped text

```text
[00:00]‏ שלום וברוכים הבאים לישיבה.
[00:12]‏ היום נדון בתקציב לשנת 2026.
```

The RLM after the bracket keeps the pair on the correct side of the Hebrew that
follows — without it, `[00:00]` can render as `]00:00[`.

## DOCX

Word takes direction from three independent places, and **all three** must be
set or the document opens left-aligned or with punctuation on the wrong side:

| Property | Level | Effect |
|---|---|---|
| `w:sectPr/w:bidi` | Section | Column and table order run right-to-left |
| `w:pPr/w:bidi` | Paragraph | The paragraph is an RTL paragraph |
| `w:rPr/w:rtl` | Run | Text is complex-script; Word uses `w:rFonts/@w:cs` and `w:szCs` |

The `Normal` style is also made RTL, so a paragraph the user adds by pressing
Enter inherits the direction.

With timestamps enabled the body is a two-column table with `w:bidiVisual`, so
the first column defined appears on the **right** — where a Hebrew reader
starts.

Complex-script font: **David**, the standard Hebrew serif on Windows. Word
substitutes automatically if absent.

Verified by `tests/test_exports.py::TestDocx`, which unzips the result and
asserts the XML properties are present.

## PDF

### Why this format is different

ReportLab 4.2.5 has no bidi support. Its `rl_config.rtlSupport` switch only
wires up `pyfribidi2` inside `pdfgen.textobject`, defaults to off, has no
maintained Windows build, and `Paragraph` never consults it. So Tiktuv runs the
bidi algorithm itself with `python-bidi`.

The ordering constraint that makes this correct:

1. **Wrap in logical order**, measuring with real glyph widths
   (`pdfmetrics.stringWidth`). Breaking lines on visual-order text puts the
   breaks in the wrong places.
2. **Then** convert each finished line to visual order (`get_display`).
3. Paint with `drawRightString` anchored at the right margin.

Consequence to be aware of: text copied out of the PDF comes back in visual
order. That is inherent to PDF, not a Tiktuv bug. Use TXT, DOCX or JSON when
you need to reuse the text.

### PDF fonts

The exporter looks for a Hebrew-capable TrueType font in this order:

1. `apps/backend/tiktuv/assets/fonts/*.ttf` (bundled; a file with `bold` in its
   name is used as the bold face)
2. `C:\Windows\Fonts\arial.ttf` → `david.ttf` → `tahoma.ttf`
3. `/usr/share/fonts/truetype/dejavu/DejaVuSans.ttf`
4. `/Library/Fonts/Arial.ttf`

If none is found the export fails with a clear `EXPORT_FAILED` message rather
than producing a PDF full of empty boxes.

To bundle your own, drop a `.ttf` into `assets/fonts/` — and confirm its licence
allows PDF embedding.

## SRT

```text
1
00:00:00,000 --> 00:00:04,500
שלום וברוכים הבאים לישיבה.

```

1-based indices, `HH:MM:SS,mmm`, CRLF, no BOM. Cues never overlap; the shaper
enforces a 0.7 s minimum and a 7 s maximum, and splits long segments at
punctuation or on word timestamps when available.

## WebVTT

```text
WEBVTT

NOTE Generated by Tiktuv — local Hebrew transcription

1
00:00:00.000 --> 00:00:04.500 direction:rl align:right
שלום וברוכים הבאים לישיבה.
```

Periods rather than commas, LF endings. `direction:rl` tells conforming players
to lay the cue out RTL instead of guessing from the first strong character.

## JSON

```json
{
  "schema": "tiktuv.transcript/1",
  "job_id": "…",
  "language": "he",
  "model_id": "ivrit-ai/whisper-large-v3",
  "duration": 1830.5,
  "speakers": { "speaker_0": "דובר 1" },
  "segments": [
    {
      "id": 0,
      "start": 0.0,
      "end": 4.5,
      "text": "שלום וברוכים הבאים לישיבה.",
      "speaker": null,
      "edited": false,
      "words": [{ "text": "שלום", "start": 0.0, "end": 0.5, "probability": 0.98 }]
    }
  ]
}
```

`ensure_ascii=false`, so Hebrew is readable in the file rather than escaped to
`\uXXXX`. `words` is populated only when word timestamps were requested. The
`schema` field is versioned; additive changes keep `/1`.

## Subtitle shaping

Applies to SRT and VTT, controlled by **אורך שורת כתובית מרבי** (default 42) and
**מספר שורות כתובית מרבי** (default 2).

* Words are never broken mid-word.
* A segment exceeding the budget is split recursively, preferring a break after
  punctuation near the middle.
* Split timing uses word timestamps when present, otherwise a proportional
  estimate.
* Speaker labels are prefixed as `דובר 1: …` when diarization ran.

## Filenames

Derived from the source filename, sanitized while preserving Hebrew. Hebrew
filenames survive intact (`ישיבת הנהלה.mp3` → `ישיבת הנהלה.docx`); path
separators, Windows-illegal characters, reserved device names and bidi control
characters do not.
